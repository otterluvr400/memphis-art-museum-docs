## Business Logic

<Steps>
  <Step title="Install-time shell creation">
    `__init__.post_init_hook` calls `product.category._init_design_websites()`.
    This creates/ensures:
    - A `website.group` origin record (`ref=1111`) when the model exists.
    - A `website` record named `__design__<shell.name>` for every `website.shell`.
    - The `__header__` website record.
    - `product.category` records for each shell and links them via `website_design_id`.
  </Step>
  <Step title="Category mirroring">
    Creating, updating, or deleting a `product.category`:
    - Synchronizes a mirrored `product.public.category` (`_sync_ecom_category`).
    - Synchronizes a mirrored `pos.category` (`_sync_pos_category`).
    - Synchronizes a top-level `website.menu` with mega-menu content (`_sync_menu`).
  </Step>
  <Step title="Shell resolution on shop/category pages">
    `controllers/main.py::WebsiteSaleDesign.shop()` resolves the active design shell from the URL:
    - `/shop/category/tc1-1` → `__design__tc1`.
    - `/hyatt/shop/category/tc1-1` → `__design__hyatt__tc1`.
    Folder shells are required; the controller deliberately refuses to fall back to the origin shell for folder-prefixed paths.
  </Step>
  <Step title="Render-time shell swap">
    When a shell is resolved, `patched_render()` temporarily sets `request.website` and `request.env.context` `website_id` to the shell, then calls `ir.ui.view._render_template()` on the original template. The original website is restored in a `finally` block.
  </Step>
  <Step title="Theme/editor routing to shell">
    `WebsiteDesignViews` intercepts `/website/theme_customize_data_get`, `/website/theme_customize_data`, and `/website/save_xml`, swapping `request.website`/`request.env` to the shell derived from the HTTP referer before calling `super()`.
  </Step>
  <Step title="Menu/view mirroring">
    `_mirror_main_website_menus_to_shells()` copies the main website's `website.menu` records to each design/folder shell, prefixing local URLs with the folder slug. `_mirror_main_website_views_to_shells()` copies the `website.footer_custom` view.
  </Step>
  <Step title="Event product lifecycle">
    Creating an `event.event` creates a linked `product.template` (`event_event.py`), binds existing/new tickets to the product variant (`event_ticket.py`), and keeps product fields in sync on event write (`event_sync.py`).
  </Step>
</Steps>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Duplicate XML ID: hide_product_id_event_ticket_list">
    `views/event_views.xml` defines `hide_product_id_event_ticket_list` twice with different `inherit_id` and `arch` content. The second record overwrites the first during module install/update. Only one override will be active.
  </Accordion>
  <Accordion title="Split product.category class">
    `models/product_category.py` and `models/web_category.py` both declare `class ProductCategory` with `_name = "product.category"`. Field merging and method override order depend on import order (`__init__.py` lists `product_category` before `web_category`, so `web_category` methods win). If you add a field in one file and a method in the other, ensure both classes still load successfully.
  </Accordion>
  <Accordion title="Orphaned menu data file">
    `views/menu.md` is XML data but is not referenced in `__manifest__.py`. It will not be installed unless added to the manifest or loaded manually.
  </Accordion>
  <Accordion title="Orphaned header shell data file">
    `data/header_shell.xml` defines the `__header__` `website` record but is not listed in `__manifest__.py` `data`. It will not be installed automatically. The module's mega-menu fallback HTML will be used instead.
  </Accordion>
  <Accordion title="Header shell references an undeclared field">
    `data/header_shell.xml` sets `is_header_shell="True"` on the `__header__` record, but this field is not declared in `header_replacer`. It must be supplied by another installed module (e.g., `web_foldering_architecture`).
  </Accordion>
  <Accordion title="Hard dependency on html_editor">
    `models/ir_ui_view.py` imports `odoo.addons.html_editor.models.ir_ui_view.IrUiView`. If the `html_editor` module is unavailable the module will fail to load.
  </Accordion>
  <Accordion title="Response wrapper assumptions">
    The shop shell-swap relies on `response._wrapped__` having a `render` method. If `WebsiteSale.shop()` returns a different response type (redirect, `werkzeug.wrappers.Response`, future Odoo refactor) the assignment may fail or leak.
  </Accordion>
  <Accordion title="Shell resolution leaks">
    Folder-prefixed category URLs intentionally do **not** fall back to the origin shell. If `__design__<folder>__<bucket>` is missing, the page renders without shell theming. This is by design but can look like a bug to users.
  </Accordion>
  <Accordion title="Generic field name collisions">
    Variables named `name`, `slug`, `category`, and `shell` are reused across controllers, models, and helpers. Always verify model context before editing.
  </Accordion>
  <Accordion title="Empty POS popup XML override">

## Native Odoo 19 Comparison

### `website.sale_product_domain`

**Native Odoo 19:** `website.sale_product_domain()` returns the standard eCommerce domain for published products on the current website.

**This module:** `models/website.py` intersects the native domain with `["|", ("date_end", "=", False), ("date_end", ">=", fields.Date.today())]`, hiding event-linked products whose end date has passed.

**Why it matters:** Event products become unavailable for purchase after the event ends, which is not default website_sale behavior.

### `event.event.create`

**Native Odoo 19:** Events and tickets are managed independently of products unless `event_product` is installed; even then, products are typically created/configured manually on ticket types.

**This module:** `models/event_event.py` automatically creates a `product.template` for every new `event.event`, binds existing tickets to the product variant, and writes back `event.product_id`.

**Why it matters:** The ERP treats events as first-class saleable products without requiring manual product configuration per event.

### `product.template._compute_website_url`

**Native Odoo 19:** Computes `/shop/<slug>-<id>` for all eCommerce products.

**This module:** For products linked to an event, overrides the computed URL to `/event/<event_id>`.

**Why it matters:** Event-linked products redirect customers to the event page instead of the product detail page.

### `WebsiteSale.shop()` render override

**Native Odoo 19:** Renders the shop page using the current website's views, theme options, and categories.

**This module:** Detects a category-specific or folder-specific design shell and monkey-patches `response._wrapped__.render` to render the same template under a different `request.website` (the shell).

**Why it matters:** It enables per-category visual layouts while keeping one physical product catalog, but it relies on internal response wrapping that is not a public API.

### `/website/theme_customize_data*` and `/website/save_xml`

**Native Odoo 19:** Theme customization and view saves target the current website in the request context.

**This module:** Controllers derive the intended shell from the HTTP referer and swap `request.website`/`request.env.context` before calling the native implementation.

**Why it matters:** Theme edits on `/hyatt/shop/category/...` are written to `__design__hyatt__tc1` rather than the main website or the folder base website.

### `website.menu` synchronization

**Native Odoo 19:** Menus are scoped to a single website. Multi-website setups maintain independent menu trees.

**This module:** `product.category` CRUD keeps a top-level website menu in sync, and `_mirror_main_website_menus_to_shells()` clones the main menu tree to every design/folder shell, rewriting local URLs with folder prefixes.

**Why it matters:** Folder websites (e.g., `/hyatt`) can share the main navigation structure while keeping folder-scoped links, but menu changes on the main site require re-mirroring.

### POS event ticket domain

**Native Odoo 19:** `pos_event` loads event tickets based on the event state and ticket availability.

**This module:** `_load_pos_data_domain` adds `("event_id.is_published", "=", True)`, preventing unpublished events from appearing in the POS.

**Why it matters:** POS operators only see events explicitly marked visible on the website.

### Event registration popup

**Native Odoo 19:** The POS event registration popup shows per-ticket and per-order questions with blank/default values.

**This module:** An OWL patch auto-fills `name`, `email`, and `phone` questions from the current order's partner.

**Why it matters:** Reduces manual data entry during POS event sales.
