# Mobile POS Relayout

Mobile POS Relayout (`mobile_pos_relayout`) changes the mobile Point of Sale UI and adds a full-screen client action that embeds the POS UI alongside the event barcode scanner and a customer/ticket search panel.

## Business Logic

### Mobile POS relayout

<Steps>
  <Step title="Cart button opens the left pane">
    `Navbar.prototype.onClickCartButton` sets `pos.scanning = false`, navigates to `ProductScreen` if not already there, and sets `pos.mobile_pane = 'left'` (the order-lines pane on mobile).
  </Step>
  <Step title="Register button opens the right pane">
    `Navbar.prototype.onClickRegisterButton` ensures an order exists (creating one if needed), navigates to `ProductScreen`, and sets `pos.mobile_pane = 'right'` (the product/register pane on mobile).
  </Step>
  <Step title="New order from burger menu">
    `Navbar.prototype.addNewOrder` creates a new order via `pos.addNewOrder()` and navigates to the order screen with `pos.navigateToOrderScreen(order)`.
  </Step>
  <Step title="Review button replaced and pricelist shown">
    On `ProductScreen`, the inherited template replaces the native review button with a `Customer` button. The JS patch adds `specialPricelist`, which displays the order partner's non-default pricelist (e.g. Members) beneath the customer name on the button.
  </Step>
</Steps>

### Free-admission checkout (event booth)

<Steps>
  <Step title="Payment screen hidden during transition">
    `pos_license_scan.js` adds `mam-free-pay-transition` to `document.body` **before** calling `payCash()`. The class hides `.payment-screen` via `EVENT_BOOTH_free_payment_flash.scss`. A 4-second safety timer clears the class if the flow is intercepted (e.g. membership guard). After `payCash()` resolves, `requestAnimationFrame` double-clears the class on the next frame so the receipt is never affected.
  </Step>
  <Step title="Background sync overlay management">
    `EVENT_BOOTH_free_checkout.js` patches `OrderPaymentValidation` to call `beginFreeBackgroundSync()` before `mamPersistAndSyncFreeOrder()` and `endFreeBackgroundSync()` in `.finally()`. While any sync is in flight, `mam-free-sync-in-flight` is set on `document.body`, which hides the pending-sync navbar overlay so rapid-fire door scanning is never covered.
  </Step>
  <Step title="Receipt status tracking">
    `EVENT_BOOTH_free_receipt_status.js` tracks free-background checkout UUIDs in a `Set` and patches `ReceiptScreen` to expose `mamFreeBackgroundCheckout`. The SCSS hides the pending-sync spinner only for free-background receipts and during active background syncs.
  </Step>
</Steps>

### POS + Scanner wrapper

<Steps>
  <Step title="Client action loads">
    `PosScannerWrapper` is registered as `mobile_pos_relayout.pos_scanner_wrapper`. On `setup`, it fetches the first available `pos.config` record and tracks both `posConfigId` and `hasConfigs` in state.
  </Step>
  <Step title="POS iframe or empty state">
    While configs are loading it shows `Loading POS…`. If a config exists, an iframe loads `/pos/ui/<config_id>`. If no config exists, a "No POS Config Found" message is shown.
  </Step>
  <Step title="Bottom toggle buttons">
    The green user button opens the customer search panel (`showCustomerSearch = true`). The primary toggle button switches `showPos`, which alternates the POS iframe and the event scanner (`showScanner = !showPos && !showCustomerSearch`).
  </Step>
  <Step title="Customer search">
    `CustomerSearchPanel` performs a debounced (250 ms) `searchRead` on `res.partner`. The domain changes based on query shape: email-only, phone-like, or a general set of fields. Selecting a partner switches to `tickets` mode and loads `event.registration` records matching the partner id or email.
  </Step>
  <Step title="Ticket check-in / undo">
    Registrations in `open` or `draft` state can be marked `done` via `action_set_done`. Registrations already `done` can be reset to `open` via `action_confirm`. After a successful call the local `reg.state` is updated immediately.
  </Step>
</Steps>

<Warning>
  Field mismatch: `CustomerSearchPanel.searchPartners` reads `name`, `email`, `phone`, and `company_name` from `res.partner`, but the template also references `partner.mobile`. Because `mobile` is not fetched, the mobile number will only render if it happens to be cached from a previous read. Confidence: **low**.
</Warning>

## Native Odoo 19 Comparison

### `point_of_sale.Navbar` cart/register behavior

**Native Odoo 19:** The navbar uses `onClickRegister()` and the mobile `mobile_pane` toggle to switch between left (cart) and right (register) panes. The review button on `ProductScreen` opens the order/cart pane.

**This module:** Adds separate `onClickCartButton` and `onClickRegisterButton` handlers, explicitly sets `pos.mobile_pane` to `'left'` or `'right'`, and replaces the review button with a customer button. The XML patch still delegates to native `onClickRegister()` on non-mobile screens.

**Why it matters:** The native two-pane toggle is split into explicit cart and register destinations. Developers updating the POS mobile state should update both the method and the pane assignment.

### `point_of_sale.ActionpadWidget` partner button

**Native Odoo 19:** The partner selection button is always visible in the action pad.

**This module:** Hides `SelectPartnerButton` when `ui.isSmall` is true, because partner selection is reached through the new customer button on the product screen.

**Why it matters:** On mobile, the action pad no longer provides the standard partner entry point. Any flow that relies on that button being present on small screens will fail.

### `point_of_sale.Navbar` burger menu

**Native Odoo 19:** The navbar dropdown menu does not include a "New Order" item.

**This module:** Adds a `DropdownItem` that calls `Navbar.prototype.addNewOrder()`.

**Why it matters:** A new convenience entry point is added to the existing menu; existing keyboard / screen-reader expectations may need testing.

### POS + event scanner wrapper

**Native Odoo 19:** The POS and event registration desk are separate apps/actions. There is no built-in action that embeds the POS UI inside an iframe next to the event barcode scanner.

**This module:** Creates a full-screen client action (`mobile_pos_relayout.pos_scanner_wrapper`) that embeds the POS UI in an iframe, overlays the event scanner, and provides a customer/ticket search panel.

**Why it matters:** This is a custom composite action that couples three independent subsystems. Changes to the event scanner action, the POS UI route, or iframe sandboxing may break the wrapper.

### Customer/ticket search panel

**Native Odoo 19:** Event registrations are managed through the event backend forms and the registration desk.

**This module:** Implements a lightweight frontend search panel that reads `res.partner`, fetches `event.registration` records by partner/email, and calls `action_set_done` / `action_confirm` directly from the UI.

**Why it matters:** This bypasses the normal event backend views and any validation or business logic that may be enforced there. It also sorts registrations locally using a hard-coded state priority (`open`, `draft`, `done`, `cancel`) rather than server-side ordering.

### `point_of_sale.ProductScreen` customer button and pricelist

**Native Odoo 19:** The `ProductScreen` action pad includes a review button that opens the order/cart pane. Partner selection is handled separately.

**This module:** The review button is replaced with a customer button, and the JS patch adds a `specialPricelist` getter that surfaces the order partner's non-default pricelist directly on the customer button.

**Why it matters:** Staff can see at a glance that a member/customer-specific pricelist is in effect, and can open partner selection from the same control. The patch depends on `currentOrder.getPartner().property_product_pricelist`, which is standard on commercial partners, but should be verified if the partner model is customized.
