## Business Logic

<Steps>
  <Step title="Event end date is set on `event.event`">
    `event.event._compute_event_has_passed` evaluates whether `date_end` is
    before today (using the record's context date). The result is stored in
    `event_has_passed`.
  </Step>
  <Step title="Event-linked product flags are recomputed">
    `product.template._compute_event_flags` evaluates the linked
    `event_id.date_end` and `event_id.event_ticket_ids`. It sets
    `event_has_passed` when the event end is before `fields.Datetime.now()` and
    `event_has_no_tickets` when the event exists but has no tickets.
  </Step>
  <Step title="POS session loads product data">
    `product.template._load_pos_data_domain` first searches every
    event-linked product (`event_id != False`) and calls
    `_compute_event_flags()` to refresh the stored flags at session load time.
    It then calls `super()._load_pos_data_domain(data, config)` and appends
    `[("event_has_passed", "=", False), ("event_has_no_tickets", "=", False)]`
    to the returned domain.
  </Step>
  <Step title="POS catalog filters out ineligible event products">
    Products whose event has ended or has no tickets are excluded from the
    products returned to the POS session.
  </Step>
</Steps>

<Info>
  The stored flags are only guaranteed fresh at POS session load. Between
  session loads, time passing can make an `event_has_passed` value stale until
  the next `_load_pos_data_domain` call.
</Info>

## Troubleshooting

- **Event product still appears in POS after the event ends:** The computed
  flags are `store=True` and only refreshed when `product.template._load_pos_data_domain`
  runs. If a product is cached in the POS client or loaded through a different
  code path, the new domain filter may not apply until the session is reloaded.
  Confidence: **medium** — inferred from the manual recompute pattern.

- **Inconsistent "passed" thresholds:** `event.event` compares
  `date_end.date()` against `fields.Date.context_today`, while
  `product.template` compares the raw `date_end` datetime against
  `fields.Datetime.now()`. An event ending today may be considered not-yet-passed
  by the event record but already passed by the product record, depending on the
  user's timezone and the current time.

- **`event_id` field missing on products:** The logic assumes `event_sale` (or
  a module in its dependency chain) is installed. If `website_event_sale` is
  removed from `depends` without replacing it with `event_sale`, the
  `product.template.event_id` field and `event.event.event_ticket_ids` field
  may not exist, causing the computes to fail or the module to refuse upgrading.

- **`_load_pos_data_domain` override not called:** If the parent model from
  `point_of_sale` changes the method name or signature in a future version, the
  override will silently stop filtering event products. The current code relies
  on the inherited method existing on `product.template`.

## Native Odoo 19 Comparison

### `event.event` event-passed indicator

**Native Odoo 19:** `event.event` provides `date_begin`, `date_end`, and a
`state` field (`new`, `confirm`, `done`, `cancel`). The end of an event is
stored on `date_end`, but there is no built-in stored boolean that says "this
event has passed." UI filters and sales flows typically rely on `state` or on
comparing `date_end` at query time.

**This module:** Adds a stored computed boolean `event_has_passed` on
`event.event` that evaluates `date_end.date() < today`. The field is shown
read-only on the event form.

**Why it matters:** Other modules can search or reference a persistent
`event_has_passed` flag instead of recomputing the date comparison themselves,
but they must remember the value can become stale if not refreshed.

### `product.template` event eligibility flags

**Native Odoo 19:** `product.template` in the event-sale dependency chain has
an `event_id` field linking a product to an event. The product catalog and POS
product loader do not, by default, hide products whose event has ended or has
no tickets.

**This module:** Adds `event_has_passed` and `event_has_no_tickets` booleans
on `product.template`, computes them from the linked event, and appends filters
for both fields to the POS product loader domain.

**Why it matters:** Event products that are no longer sellable are removed from
the POS product grid automatically, reducing the chance of selling tickets for an
expired event or for an event without configured tickets.

### `product.template._load_pos_data_domain`

**Native Odoo 19:** The POS session loader calls `_load_pos_data_domain` to
build the domain of products sent to the POS frontend. The base implementation
returns a domain that limits products by availability-in-POS and sale-OK status,
plus module-specific criteria.

**This module:** Overrides `_load_pos_data_domain` to force a one-time refresh
of every event-linked product's flags (`self.search([("event_id", "!=", False)])._compute_event_flags()`),
then extends the parent domain with
`[("event_has_passed", "=", False), ("event_has_no_tickets", "=", False)]`.

**Why it matters:** This is the only place where the stored flags are guaranteed
to be fresh relative to wall-clock time. Developers adding new product-loading
paths should apply the same domain filters or refresh the flags before use.
