## Business Logic

### Registration page setup

<Steps>
  <Step title="Controller prepares lightweight values">
    `WebsiteEventCalendarSlotsController._prepare_event_register_values(event, **post)` (`controllers/main.py`) overrides the parent method and returns a dict with:
    - `event`, `main_object`, `range`, `google_url`, `iCal_url`, `registration_error_code` (forwarded from base/parent patterns)
    - `slots: {}` — deliberately empty; slots are loaded on demand by the JS calendar
    - `calendar_slots_json: json.dumps({"date_tz": event.date_tz})` — JSON payload consumed by the calendar interaction
    - `website_visitor_timezone` — via `request.env["website.visitor"]._get_visitor_timezone()`
  </Step>
  <Step title="Calendar requests a range summary">
    The interaction calls `/event/<event>/slots/summary` with `start` and `end` ISO dates. The controller searches `event.slot` for the event between those dates, calls `_filter_open_slots()`, and returns a per-date summary (`count` and `sold_out` boolean).
  </Step>
  <Step title="User selects a day">
    The interaction calls `/event/<event>/slots/day` with a single `date`. The controller returns full slot records (`id`, `start_datetime`, `end_datetime`, `is_sold_out`). The result is cached in `dayCache`.
  </Step>
  <Step title="User selects a slot and submits">
    Selecting a slot sets `data-selected-slot-id` on the form. Submitting calls `rpc(formEl.action.replace("slot_id", this.selectedSlotId))` and injects the returned modal HTML into the document body.
  </Step>
</Steps>

### Calendar interaction

## Security

No security files were found in this module. Access to `event.slot` is performed via `sudo()` in both controller routes, so record-level rules on `event.slot` are bypassed for public users. The public routes rely on:

- The event record being reachable via the `model("event.event")` converter (standard `website_event` access).
- The `_filter_open_slots()` method to exclude unavailable slots.

<Warning>
  Confidence: **high** that no `security/` files exist. Because `sudo()` is used, any public visitor can read slot counts and details for any event whose slug/id is known. Verify whether this is the intended security posture.
</Warning>

### `WebsiteEventController._prepare_event_register_values`

**Native Odoo 19:** Likely prepares the event registration page with a list/dropdown of available slots and passes slot records directly to the template for server-side rendering.

**This module:** Overrides the method to return an empty `slots` dict and a small JSON payload (`calendar_slots_json`). Slots are loaded asynchronously by the frontend interaction.

**Why it matters:** The registration page is no longer self-contained; it requires JavaScript execution and two extra JSON endpoints to populate the calendar. Server-side fallback is minimal.

### `website_event.modal_slot_registration` template body

**Native Odoo 19:** Likely renders a modal with a list/table of selectable slot options (server-side QWeb loop over `slots`).

**This module:** Replaces the entire modal body with a custom calendar layout (`week`/`month`/`year` buttons, previous/next navigation, day grid, and a per-day slot detail panel).

**Why it matters:** Any upstream template change or translation in the modal body is overwritten. Developers should diff against the parent template after each Odoo upgrade.

### `public.interactions` registry entry `website_event.slot_details`

**Native Odoo 19:** Likely registers an interaction named `website_event.slot_details` that handles the native slot list (selection, form submit, etc.).

**This module:** Removes the native interaction and registers `website_event.slot_details_calendar` with the same selector.

**Why it matters:** The replacement is intentional but brittle; if other modules extend `website_event.slot_details`, those extensions will be lost unless they also target the new registry key.
