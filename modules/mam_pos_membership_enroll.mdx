## Business Logic

<Steps>
  <Step title="Phone Normalization">
    `to_e164()` strips non-digits, handles US 10/11-digit numbers, and produces E.164 format (`+1XXXXXXXXXX`). Variants (raw, E.164, stripped leading 1) are collected for partner matching.
  </Step>
  <Step title="Partner Resolution">
    `_find_partner()` searches by any phone variant or `phone_sanitized`. If no match, `_create_partner()` creates a minimal partner with the phone number as name (flagged for cleanup).
  </Step>
  <Step title="Subscription Check">
    `_find_active_subscription()` looks for any active subscription (`3_progress`, `4_paused`, `5_renewed`). If found, the partner is treated as already a member and no new subscription is created. This protects paid members from accidental downgrades.
  </Step>
  <Step title="Subscription Creation">
    `_create_subscription()` creates a `sale.order` with the resolved $0 recurring product, forces `price_unit = 0.0`, assigns the plan explicitly, and calls `action_confirm()`. Confirmation triggers `mam_membership_loyalty` to assign the benefit pricelist and `mam_membership_cards` to create the card.
  </Step>
  <Step title="Card Assertion">
    `_assert_card()` calls `partner._sync_benefit_pricelist()` and `partner._sync_membership_card()`, then fetches the card via `_get_or_create_for_partner()`. If the card is inactive or linked to a different subscription, it is updated.
  </Step>
  <Step title="SMS Delivery">
    `_send_card_sms()` builds the card link from `mam_membership_enroll.card_link_base` (or `web.base.url`) and sends via `sms.sms`. Both `sent` and `pending` states are treated as success (Mandrill never sends delivery webhooks).
  </Step>
  <Step title="Entry Point">
    `enroll(phone)` is idempotent: partner/subscription/card are find-or-create. Only the SMS repeats on retry.
  </Step>
</Steps>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Enrollment fails with 'No recurring product named Local Pass'">
    The product must be named exactly "Local Pass", have `recurring_invoice = True`, and have a `benefit_pricelist_id` set. Alternatively, set the `mam_membership_enroll.product_id` system parameter to the product ID directly.
  </Accordion>
  <Accordion title="Enrollment fails with 'No subscription plan named Yearly'">
    Create a plan named exactly "Yearly" or set `mam_membership_enroll.plan_id`.
  </Accordion>
  <Accordion title="SMS shows as failed but message was delivered">
    The Mandrill transport never sends delivery-report webhooks. Odoo 19 leaves successful handoffs in `pending` state. The code treats both `sent` and `pending` as success; any other state is a failure.
  </Accordion>
  <Accordion title="Partner created with phone number as name">
    This is intentional — the comment says "obvious cleanup marker for DB personnel". The DB crew is expected to merge or clean up these records.
  </Accordion>
  <Accordion title="Benefit pricelist not assigned after enrollment">
    Ensure `mam_membership_loyalty` is installed. It is not a declared dependency but is responsible for pricelist assignment on subscription confirmation.
  </Accordion>
</AccordionGroup>

## Native Odoo 19 Comparison

### POS session extension

**Native Odoo 19:** `pos.session` has no membership enrollment method.

**This module:** Adds `action_enroll_membership_from_pos()` as a clean entry point that delegates to the abstract service.

**Why it matters:** Keeps POS UI code thin; all business logic is centralized in `mam.membership.enroll`.

### Subscription creation

**Native Odoo 19:** `sale_subscription` requires manual order creation or website checkout.

**This module:** Programmatically creates a $0 subscription with explicit plan assignment and forced zero pricing.

**Why it matters:** Enables at-the-door enrollment without website interaction.
