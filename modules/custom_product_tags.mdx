## Business Logic

<Steps>
  <Step title="Create a tag category">
    A user creates a `product.custom.tag.category` record with a unique `name`.
  </Step>
  <Step title="Create a custom tag">
    A user creates a `product.custom.tag` record, selecting a `category_id` and entering a `sub_name`. The `name` field is automatically computed as `category_id.name:sub_name` and stored. A Python constraint prevents duplicate `sub_name` values within the same category.
  </Step>
  <Step title="Assign a tag line to a product template">
    On the product form, inside the `Custom Tags` notebook page, the user adds a `product.tag.line` row, chooses a `category_id`, then chooses a `tag_id` filtered by that category. The onchange `_onchange_category_id` resets `tag_id` whenever the category changes. A Python constraint prevents the same product from having the same `category_id + tag_id` combination twice.
  </Step>
</Steps>

## Troubleshooting

- **Menu not visible:** Ensure the `sale` module is installed and `sale.product_menu_catalog` exists in the target environment. If `sale` were removed from `depends`, the menu would fail to render or raise a dependency error during upgrade.
- **Category manager access missing:** Only users in `sales_team.group_sale_manager` can create or edit categories. Regular users can only read categories and manage tags/lines.
- **Duplicate tag error on data import:** The `product.custom.tag` model requires unique `category_id + sub_name` pairs, and `product.tag.line` requires unique `product_tmpl_id + category_id + tag_id` triples. Imports must de-duplicate these keys.
- **Onchange vs stored value mismatch:** <Warning>Confidence: **low** — inferred runtime state, not verified.</Warning> The `tag_id` domain in the view and the onchange both rely on `category_id`. If the `category_id` of a tag is changed after a `product.tag.line` has already referenced it, the existing line may hold a tag that no longer belongs to the chosen category. There is no constraint to enforce consistency between `category_id` and `tag_id.category_id` on the line itself.

## Native Odoo 19 Comparison

### `product.template` tagging

**Native Odoo 19:** Native Odoo provides a `product.tag` model (flat, single-level tags, usually with a `name` and a `color` field) and a `Many2many` field `product_tag_ids` on `product.template`. Tags are global, non-hierarchical, and can be applied directly to products without a category or intermediate line model.

**This module:** The module introduces a three-level hierarchy: `product.custom.tag.category` → `product.custom.tag` → `product.tag.line`. Tags are scoped to a category, and product assignments are stored as separate `product.tag.line` records (One2many on `product.template`), each carrying a category, a sub-category tag, and an optional note.

**Why it matters:** The native model supports quick, flat classification; this module supports structured classification where each product can have at most one tag per category and assignment records carry extra metadata (`note`). Developers integrating with other modules should query `product.tag.line` rather than native `product.tag` or `product_template.product_tag_ids`.

### `product.custom.tag.name` vs native display-name behavior

**Native Odoo 19:** The `product.tag` model uses the standard `name` Char field as the display name, and records are typically shown as colored pills in the UI.

**This module:** The `product.custom.tag` model sets `_rec_name = "sub_name"` and uses a stored computed `name` field that concatenates `category_id.name` and `sub_name`. The list view displays both the raw `sub_name` and the composite `name`.

**Why it matters:** Because `sub_name` is the display name, search defaults, many2one dropdowns, and x2m list references will show the sub-category without the category prefix unless the UI explicitly includes the `name` field. Forms show the computed `name` as read-only to avoid manual edits.
