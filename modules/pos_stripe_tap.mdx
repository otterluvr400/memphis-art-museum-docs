# POS Stripe Tap to Pay

`pos_stripe_tap` registers a new POS payment terminal type called **Stripe Tap (Android M2)** and wires it to the native Stripe Terminal SDK through an Android POS JavaScript bridge. It adds a small Python model override, one JSON controller for Stripe connection tokens, and a single OWL patch on the `ProductScreen`.

**File:** `models/pos_payment_method.py`

After a successful membership charge, retrieves the PaymentIntent (with `expand[]=latest_charge`), extracts the reusable `generated_card` payment method, and creates an Odoo `payment.token` linked to the partner. Returns the token id, or `None` if no reusable card method exists.

#### `pos.payment.method.stripe_tap_create_subscription(...)`

**File:** `models/pos_payment_method.py`

Each distinct plan becomes a separate subscription order with one line per matching product. The order is confirmed, the signature (if captured) is written to `x_studio_binary_field_88l_1jvc90oua`, and `next_invoice_date` is advanced if it equals `start_date` (prepaid at POS).

## Business Logic

### Registering the terminal type

<Steps>
  <Step title="Payment method form loads terminal choices">
    Odoo calls `pos.payment.method._get_payment_terminal_selection()` to populate the **Use a Payment Terminal** field.
  </Step>
  <Step title="Stripe Tap appears as an option">
    The override appends `("stripe_tap", "Stripe Tap (Android M2)")` to the native list.
  </Step>
</Steps>

### Processing a Stripe Tap payment

<Steps>
  <Step title="Cashier validates a Stripe Tap order">
    `ProductScreen.fastValidate` is invoked when the configured payment method uses a terminal.
  </Step>
  <Step title="Contact-info and signature capture">
    For membership sales, the flow opens `ContactInfoPopup` (email/phone) and `SignaturePopup` to capture customer contact data and a recurring-billing authorization signature.
  </Step>
  <Step title="Plan selection">
    `MembershipPlanPopup` displays the available `product.pricelist.item` plans for each membership product, including prorated first-charge amount, and lets the cashier select which plans to subscribe to. Radio inputs use `tabindex="-1"` and `pointerdown.prevent` to prevent iOS click-through and double-trigger issues.
  </Step>
  <Step title="Build payment parameters">
    For a Stripe Tap order, it reads:
    - `amountCents` = `Math.round(order.totalDue * 100)`
    - `currency` = lowercase `this.pos.currency.name` (defaults to `"usd"`)
    - `orderRef` = `order.pos_reference || order.uid`
  </Step>
  <Step title="Create PaymentIntent server-side">
    `pos.payment.method.stripe_tap_create_intent()` creates a Stripe Terminal PaymentIntent via the configured payment provider. If a customer id is available and the order qualifies for card-on-file, `customer` and `setup_future_usage=off_session` are attached.
  </Step>
  <Step title="Call Android POS bridge">
    `stripeTapPay` checks for `window.AndroidPos`. If missing, it rejects with an error. Otherwise it sets a one-time `window.onStripePaymentResult` callback and calls `AndroidPos.payWithStripe(amountCents, currency, orderRef, clientSecret)`.
  </Step>
  <Step title="Resolve or reject">
    The Android wrapper invokes `window.onStripePaymentResult(success, paymentIntentId, error)`. On success, the promise resolves with the Stripe `paymentIntentId`; on failure, it rejects with the provided error message.
  </Step>
  <Step title="Tokenize and create subscription">
    On success, the backend tokenizes the card (`stripe_tap_tokenize`) and creates subscription sale orders (`stripe_tap_create_subscription`). A portal user is generated and credentials are emailed/SMSed.
  </Step>
  <Step title="Complete native validation">
    If `stripeTapPay` succeeds, the patch calls `super.fastValidate(paymentMethod)` to finalize the order in Odoo. If it fails, a danger notification is shown and the validation aborts.
  </Step>
</Steps>

### Membership subscription creation

<Steps>
  <Step title="Identify membership products">
    Products whose category matches membership category ID `8` have `recurring_invoice` auto-enabled by `product.template` overrides.
  </Step>
  <Step title="Resolve plan rules">
    `stripe_tap_create_subscription` searches `product.pricelist.item` records with `plan_id` for those templates.
  </Step>
  <Step title="Create one sale.order per plan">
    Each plan becomes a confirmed subscription order with `is_subscription=True`, `plan_id`, `payment_token_id`, and the selected product line(s).
  </Step>
  <Step title="Advance next invoice when prepaid">
    If `next_invoice_date <= start_date`, the order is advanced one period because the first charge already happened at the register.
  </Step>
  <Step title="Portal access">
    A portal user is created and the generated password is stored on the partner and on the created orders.
  </Step>
</Steps>

### Blackbaud renewal sync

<Steps>
  <Step title="Subscription auto-renews">
    Odoo subscription renewal cron calls `sale.order._do_payment()`.
  </Step>
  <Step title="Payment succeeds">
    If any transaction has `state == "done"` and the order is a subscription with membership-category products, the hook runs.
  </Step>
  <Step title="Enqueue renewal in Blackbaud">
    `mam.blackbaud.source.enqueue_membership_sync(operation="renewal", ...)` is called with the partner's email, name, phone, and membership product names.
  </Step>
</Steps>

<Warning>
  The `mam_integration_hub` soft dependency is checked at runtime. If the module is not installed, the renewal sync silently no-ops.
</Warning>

### Connection-token endpoint

<Steps>
  <Step title="Client requests a token">
    The Android POS app or a frontend client POSTs to `/pos_stripe_tap/connection_token`.
  </Step>
  <Step title="Controller reads Stripe key">
    `StripeTapController.connection_token` fetches `stripe.secret_key` from `ir.config_parameter` via `sudo`.
  </Step>
  <Step title="Stripe Terminal token created">
    It calls `stripe.terminal.ConnectionToken.create()` and returns `{ "secret": token.secret }`.
  </Step>
</Steps>

### Keepalive SetupIntent endpoint

<Steps>
  <Step title="Client requests a keepalive SetupIntent">
    The Android app POSTs to `/pos_stripe_tap/keepalive_setup_intent` to generate a zero-amount reader activity intent.
  </Step>
  <Step title="Controller reads Stripe key">
    `StripeTapController.keepalive_setup_intent` fetches `stripe.secret_key` from `ir.config_parameter` via `sudo`.
  </Step>
  <Step title="SetupIntent created">
    It calls `stripe.SetupIntent.create(payment_method_types=["card_present"], usage="off_session")` and returns `{ "client_secret": si.client_secret }`.
  </Step>
</Steps>

<Warning>
  The keepalive endpoint creates a SetupIntent with no customer and no amount. Even if a card lands in the app's 1-second collect window, nothing can be charged. The saved-payment-method half of the object is never used.
</Warning>

<Warning>
  The controller uses `sudo()` to read the system parameter. Any authenticated Odoo user who can reach the route can trigger a Stripe connection-token creation. Confidence: **medium**.
</Warning>

## Native Odoo 19 Comparison

### `pos.payment.method._get_payment_terminal_selection`

**Native Odoo 19:** The base implementation returns the list of supported payment terminals, e.g., `stripe`, `adyen`, `six`, etc., depending on installed modules.

**This module:** Appends `("stripe_tap", "Stripe Tap (Android M2)")` to the list.

**Why it matters:** Odoo 19 ships a native `pos_stripe` integration that uses Stripe readers through a different frontend/backend architecture. This module adds a parallel terminal type that uses a custom Android bridge rather than the native Stripe Terminal flow.

### `ProductScreen.fastValidate`

**Native Odoo 19:** `fastValidate` initiates the configured payment terminal flow (e.g., Stripe, Adyen) through the native terminal abstraction and completes the order.

**This module:** For `stripe_tap` only, it intercepts validation, converts the order total to cents, and delegates card capture to `window.AndroidPos.payWithStripe`. Only after the bridge reports success does it fall through to the native `fastValidate` to finalize the order.

**Why it matters:** The custom flow bypasses the native terminal abstraction and relies on a non-standard global JS bridge. It also changes the currency handling: if `this.pos.currency.name` is missing, the helper defaults to `"usd"`, which may not match the company's actual currency.

### Stripe Terminal connection-token flow

**Native Odoo 19:** The `pos_stripe` module provides its own backend controllers, payment-method model, and frontend service for discovering Stripe readers and creating payment intents.

**This module:** Implements a single minimal controller (`/pos_stripe_tap/connection_token`) that creates a Stripe Terminal `ConnectionToken` from a system parameter. Reader discovery, payment-intent creation, and capture happen inside the Android wrapper, not Odoo.

**Why it matters:** The integration is intentionally thin on the Odoo side. Most of the Stripe Terminal lifecycle is handled by the Android host, which limits visibility for Odoo developers when a payment fails or needs to be reconciled.
