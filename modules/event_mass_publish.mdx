### `event.publish.job`

- Inherits `mail.thread` for chatter (`chatter` widget is present in the form view).
- `_order = "create_date desc"`.
- The `name` field defaults to the next value from the `event.publish.job` sequence
  (`seq_event_publish_job`), with fallback `"New"`.
- Computed counters depend on `line_ids.state` and are stored in the database.

### `event.publish.job.line`

- Each line represents one event to publish or unpublish.
- `error` is populated when `_process_lines` catches an exception for that line.
- Deleting a line via `action_exclude_selected` removes it from the job entirely.

### `event.publish.status`

- Read-only view (`_auto = False`) backed by `_table_query`.
- Joins `event_event`, `product_template`, and `event_event_ticket` to show whether
  an event, its tickets, and its linked product are all published.
- `pos_ready` is `True` only when `event.is_published`, all tickets are published, and
  the linked product is published.

## Business Logic

<Steps>
  <Step title="Create a job from selected events">
    `action_queue_from_selection(event_ids, publish=True, batch_size=None)` creates
    an `event.publish.job` in state `running`, preloads one `event.publish.job.line`
    per selected event, and posts a chatter message. If the selection has 200 or fewer
    events (`INLINE_LIMIT`), it immediately calls `_process_lines` and
    `_finalize_if_drained`.
  </Step>
  <Step title="One-click publish-all workflow">
    `action_new_publish_all()` creates a draft job and opens its form. The user then
    runs `action_load_events()` to load every event whose `is_published` does not
    match the job's `publish` flag, and `action_start()` to process lines within a
    45-second inline budget.
  </Step>
  <Step title="Processing a batch">
    `_process_lines(lines, deadline=None)` iterates the lines, writes the event's
    `is_published` to the job's `publish` value, and marks each line `done` or
    `failed`. Each line is wrapped in a savepoint so a failure on one event does not
    roll back the entire batch.
  </Step>
  <Step title="Finalizing">
    `_finalize_if_drained()` checks for remaining `pending` lines. If none remain and
    any line failed, the job becomes `partial` (or `failed` if nothing succeeded).
    Otherwise it becomes `done`.
  </Step>
  <Step title="Cron drain">
    `_cron_process_publish_jobs()` finds the oldest `running` job, processes up to
    `batch_size` pending lines, posts a message, and finalizes. One cron pass only
    drains one job.
  </Step>
</Steps>

### Additional logic

- `action_load_events()` only loads events whose `is_published` differs from the job's
  `publish` flag. It skips events already present in the job.
- `action_cancel()` cancels `pending` lines and sets the job state to `cancelled`.
- `action_retry_failed()` and `action_requeue_selected()` reset `failed` lines to
  `pending` and clear the `error` field.
- `action_exclude_selected()` deletes `pending` lines chosen from the line list via
  `active_ids` context.

<Warning>
  `action_exclude_selected` and `action_requeue_selected` rely on `active_ids` being
  present in the context. If called without a selection, they act on no records
  without raising an error. Confidence: **medium**.
</Warning>

## Troubleshooting

<Warning>
  These are inferred from the code, not verified at runtime. Confidence: **low**.
</Warning>

- **Hard-coded limits:** `DEFAULT_BATCH_SIZE = 50`, `INLINE_LIMIT = 200`, and
  `START_BUDGET_SECONDS = 45`. Changing volume or load may require adjusting these.
- **Cron backlog:** only one running job is processed per cron pass, and only up to
  `batch_size` pending lines. Large jobs may take many minutes to drain because the
  cron interval is one minute.
- **Context-dependent actions:** `action_exclude_selected` and `action_requeue_selected`
  expect `active_ids` in the context. Calling them from the wrong context silently
  does nothing.
- **Status view SQL dependency:** `event.publish.status` joins `event_event_ticket`
  and `product_template`. If the schema changes (for example, `event_event_ticket` is
  renamed or `product_id` is removed from `event_event`), the view will fail to
  install/update.
- **Cascade deletes:** `event.publish.job.line` is `ondelete="cascade"` on both
  `job_id` and `event_id`. Deleting an event or job deletes its lines.
- **Missing product:** `event.publish.status` handles `product_id` being `NULL` by
  treating `product_ok` and `pos_ready` as `False`, but the UI still shows the row.

## Native Odoo 19 Comparison

### `event.event.is_published`

**Native Odoo 19:** `event.event` gains an `is_published` boolean through
`website_event`. Users can publish or unpublish events individually from the event
form or via website content management.

**This module:** Adds batch wrappers (`action_queue_from_selection`,
`action_new_publish_all`, server actions) that create `event.publish.job` records
and write `is_published` for many events in one transaction, with per-line failure
isolation.

**Why it matters:** A single failed event no longer blocks the entire batch, and
operators can queue/unpublish hundreds of events from the event list view without
manual per-event clicks.

### Batch processing scheduler

**Native Odoo 19:** No built-in cron job specifically for bulk event publishing.
`is_published` is typically updated synchronously when a user saves a record.

**This module:** Provides `_cron_process_publish_jobs` and an `ir.cron` record that
runs every minute to drain `running` jobs in `batch_size` chunks, respecting a
short inline budget for interactive starts.

**Why it matters:** Long-running publish operations can be initiated interactively
and completed asynchronously, reducing UI timeouts for large selections.

### Publish-status dashboard

**Native Odoo 19:** No standard combined view shows whether an event, its tickets,
and its linked product are all published. These checks require navigating multiple
models and menus.

**This module:** `event.publish.status` is a SQL-backed read-only view that joins
`event_event`, `event_event_ticket`, and `product_template` to compute `pos_ready`
in one place.

**Why it matters:** POS or box-office staff can quickly identify events that are
published but not ready for sale because tickets or the product are still
unpublished.

### `mail.thread` on a job model

**Native Odoo 19:** `event.event` itself inherits `mail.thread` for chatter, but
there is no standard job object for batch publish operations.

**This module:** `event.publish.job` inherits `mail.thread` and records every
load, batch, finalization, cancel, retry, and failure as chatter messages on the
job record.

**Why it matters:** Each batch job has an auditable history attached to it, which
the native event record does not provide for bulk publish actions.
