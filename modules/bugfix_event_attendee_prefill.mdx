## Business Logic

<Steps>
  <Step title="User opens the attendee registration modal">
    The modal is rendered by `website_event.registration_attendee_details`.
    Each selected ticket generates a separate `.modal-body` section inside the
    `#modal_attendees_registration` element.
  </Step>
  <Step title="First-ticket fields are prefilled from the logged-in user">
    `registration_event_question_prefill` sets the value of every
    `.form-control` input to
    `default_first_attendee.get(question.question_type, '')`. In native Odoo,
    `default_first_attendee` is a dict populated from the current portal user,
    typically keyed by question type (e.g. `name`, `email`, `phone`).
  </Step>
  <Step title="User clicks Apply to All">
    The `js_apply_all_attendees` button appears only on the first ticket
    (`counter == 1`). Clicking it runs `apply_all_attendees.js`, which copies
    the value of every `input.form-control`, `select.form-select`, and
    `textarea.form-control` from the first `.modal-body` into matching fields
    of every other ticket body. Matching is based on the suffix after the first
    dash in the input `name` attribute, e.g. `"name-1"` and `"2-name-1"` both
    yield key `"name-1"`.
  </Step>
  <Step title="User submits from the top button bar">
    The submit / cancel bar is rendered at the top of the modal instead of the
    footer. The button labels and visibility mirror native logic: "Sign In" for
    mandatory-account paid tickets on public users, "Go to Payment" for paying
    tickets, and "Confirm Registration" for free tickets.
  </Step>
</Steps>

## Native Odoo 19 Comparison

### `website_event.registration_event_question` prefill

**Native Odoo 19:** The `registration_event_question` template renders
attendee-specific questions (name, email, phone, and custom event questions).
Native prefill is generally limited to the first attendee's name and email
fields via the `default_first_attendee` dict or dedicated `t-att-value`
attributes.

**This module:** Replaces the value attribute of *every* `.form-control` input
with `default_first_attendee.get(question.question_type, '')`, effectively
attempting to prefill any attendee field whose `question_type` key exists in
the dict.

**Why it matters:** Custom event questions that share a `question_type` key
with the logged-in user's portal profile data will be prefilled automatically,
which native Odoo does not do for arbitrary questions.

### `website_event.registration_attendee_details` button placement

**Native Odoo 19:** Action buttons (Confirm / Go to Payment / Cancel) live in
a `.modal-footer` at the bottom of the registration modal.

**This module:** Replaces the footer with a hidden stub and inserts an
identical button bar immediately after the modal header, styled as
`sticky-top`.

**Why it matters:** For events with many tickets or long forms, users no
longer need to scroll to the bottom to submit. Any custom CSS or JavaScript
that targets `.modal-footer` buttons will break because the visible buttons
are now in a sibling `&lt;div&gt;` after `.modal-header`.

### Multi-ticket attendee copying

**Native Odoo 19:** Each ticket's attendee fields are independent; users must
fill every ticket separately.

**This module:** Adds a "Apply to All" button that copies the first ticket's
attendee answers to all other selected tickets via the frontend script.

**Why it matters:** This changes the user experience for bulk ticket purchases
and introduces a client-side dependency on input `name` attribute parsing.
Developers should be aware that the copy is one-way (first ticket → others)
and does not validate data server-side.
