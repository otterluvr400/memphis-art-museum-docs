### Native Odoo 19 comparison — cross-module chaining

#### `ir.http._dispatch` inheritance chain

**Native Odoo 19:** A single `ir.http` abstract model is provided by the `base`/`http` stack. Custom modules can inherit it, but Odoo does not ship a folder-routing layer.

**This module:** Two custom modules (`web_foldering_architecture` and `folder_link_intercept`) both inherit `ir.http`. Because `folder_link_intercept` depends on `web_foldering_architecture`, the `super()._dispatch()` chain inside `folder_link_intercept` runs `web_foldering_architecture`'s `_dispatch` first, which rewrites redirect `Location` headers to preserve folder prefixes.

**Why it matters:** The order of modules in the inheritance chain determines whether the access gate, origin-only redirect, sticky redirect, and HTML rewriting run before or after the prefix rewriting performed by `web_foldering_architecture`. If a third module is inserted between them, redirect behavior may change.

## Business Logic

<Steps>
  <Step title="Access gate (folder-prefixed requests)">
    When a request arrives with a folder slug (via `request.folder_slug`), `_handle_folder_access_gate` validates the folder and an access code.
    - If the URL contains an `access_code` or `accesscode` query parameter, it is validated against `folder.access.code`. On success, the code is stored in session and a dedicated access cookie, the code is marked `activated=True`, and the browser is redirected to the same URL without the access-code parameter.
    - If a valid session code or cookie exists, the request is allowed to proceed and `request.folder_access_code` is set.
    - If no valid code exists, the session/cookie/promo state for that folder is cleared and a `werkzeug.exceptions.Forbidden` is raised.
  </Step>
  <Step title="Canonical redirect for origin-only paths">
    If an origin-only page (e.g., `/contactus`, `/shop/cart`, `/shop/checkout`) is accidentally requested under a folder prefix (e.g., `/hyatt/contactus`), `_origin_only_folder_prefix_redirect_url` strips the folder prefix and redirects back to the canonical origin URL.
  </Step>
  <Step title="Sticky folder redirect">
    If a request hits an ordinary public path (not origin-only, not system) and an active folder session exists, `_sticky_folder_redirect_url` redirects the browser into the folder prefix (e.g., `/shop` → `/hyatt/shop`). This keeps the user inside the folder experience for normal browsing.
  </Step>
  <Step title="Apply folder promotion code to cart">
    Before and after the normal Odoo dispatch, `_apply_session_folder_code_to_existing_cart` checks whether the request is on a relevant commerce path. If a valid folder access code exists, it calls `_apply_folder_promo_to_cart` to apply the loyalty/promotion code to the current sale order.
  </Step>
  <Step title="HTML link rewriting">
    After dispatch returns a successful HTML response, the module parses the response body with `lxml.html`, iterates every `<a>` tag, and rewrites local URLs to include the active folder slug while preserving query strings and anchors. Origin-only and system paths are excluded from prefixing.
  </Step>
</Steps>

## Troubleshooting

- **Folder requests return 403 Forbidden:** Verify that `web_foldering_architecture` is installed and that it sets `request.folder_slug` before `ir.http._dispatch` runs. Also verify that a valid `folder.access.code` record exists for the folder and that the URL includes the correct `access_code` or the browser has a valid session/cookie code.
- **Links are not rewritten:** Link rewriting only happens for successful HTML responses (`status_code == 200`, `Content-Type` contains `text/html`, no `Content-Encoding`). If the response is compressed, an error, or non-HTML, no rewriting occurs.
- **Promo code is not applied to cart:** The promo applies only on relevant paths (`/shop`, `/payment`, folder-prefixed `/shop`, `/cart`, `/checkout`, `/event`). It requires `website`, `sale`, and `loyalty` to be installed, and the cart must contain at least one discountable line. The code is not applied if the cart is empty or the access code is invalid/expired.
- **Cookie is not set:** The access cookie is set with `secure=True`, `httponly=True`, `samesite="Lax"`, and `path="/"`. On local HTTP environments the cookie may be rejected by browsers; HTTPS is required in production for the cookie to persist.
- **Origin-only redirects loop or fail:** If `request.folder_slug` is set but `web_foldering_architecture` also routes origin-only paths, the redirect logic in `_origin_only_folder_prefix_redirect_url` may conflict. Ensure origin-only paths are excluded from folder routing upstream.
- **Stale session state:** The module clears session access codes and promo state when validation fails, but dedicated access cookies survive session resets. If a folder is deleted or deactivated, the cookie may still attempt to authenticate until it expires (30 days) or is overwritten by a new valid code.
- **Debug logs appear only for specific paths:** `_folder_debug_enabled` returns `True` for paths containing `contactus`, `?enable_editor`, internal control paths, `/website`, `/web`, and `/p`. Other paths do not emit debug entries.

## Native Odoo 19 Comparison

### `ir.http._dispatch`

**Native Odoo 19:** `ir.http._dispatch` is the core HTTP routing dispatcher. It matches the route, validates authentication, invokes the endpoint, and returns the response. It does not rewrite outgoing HTML, manage folder-specific session state, or redirect based on marketing-folder slugs.

**This module:** The module overrides `_dispatch` to insert a folder access gate, canonical origin-only redirects, sticky-folder redirects, promotion-code application, and post-response HTML link rewriting before returning the response to the client.

**Why it matters:** Any bug or performance issue in this override affects every website request in the database, not just folder-prefixed pages. Developers debugging routing or response issues should check this module first, because it intercepts and mutates requests and responses before they reach the browser.

### `request.cart` and current cart resolution

**Native Odoo 19:** Odoo 19 introduced `request.cart` as the primary way to access the current website cart. Fallback methods include `website._get_and_cache_current_cart()` and `website._create_cart()` for creating a new cart on demand.

**This module:** `_get_current_sale_order` checks `request.cart`, then `_get_and_cache_current_cart`, then `_create_cart` when `force_create=True`. It also guards against creating carts during read-only database transactions.

**Why it matters:** The module needs an accurate cart reference before applying a folder promotion. If `request.cart` is missing (for example, during the first request of a session), the helper falls back to cached/created carts. On read-only requests, cart creation is skipped to avoid ` psycopg2` read-only errors.

### HTML response link rewriting

**Native Odoo 19:** Odoo does not rewrite URLs inside rendered HTML responses at the dispatcher level. URLs are generated by QWeb templates, controllers, and JavaScript as they are.

**This module:** After a successful HTML response, the module parses the entire response body with `lxml.html`, iterates every `<a>` element, and rewrites local `href` values to include the active folder slug. It preserves doctype declarations, query strings, and anchors, and it skips external URLs, system paths, and origin-only paths.

**Why it matters:** This is a global, post-render transformation. It ensures that users who entered through a folder stay in the folder as they click links, but it also adds parsing/serialization overhead to every successful HTML response and may interact unexpectedly with custom JavaScript that inspects or manipulates `href` attributes after page load.

### Promotion-code application via `sale.order._try_apply_code`

**Native Odoo 19:** The `loyalty` module provides coupon/promotion-code handling on the website and in sales orders. Standard website checkout handles code entry through the cart/payment UI.

**This module:** Folder access codes double as loyalty codes. When a valid folder session is detected, the module automatically calls `_try_apply_code` and `_apply_program_reward` on the current sale order, then tracks the result in session state (`applied`, `pending`, `removed`).

**Why it matters:** Customers do not need to manually enter a promo code; the folder access code applied at entry automatically applies its linked loyalty reward. However, the module must reconcile the session state with the actual order lines, and it intentionally stops re-applying the reward if the customer removes it from the cart.

### Access-code enforcement

**Native Odoo 19:** Odoo does not have a concept of folder-specific access codes or folder-prefixed public routes. Access control is handled by record rules, groups, and controller auth decorators.

**This module:** Folder-prefixed requests are gated by validating a `folder.access.code` record. Validation includes matching the code, checking expiration dates on both the code and its linked loyalty card, and verifying the card is active. On failure, the module raises `Forbidden` and clears session/cookie state for the folder.

**Why it matters:** The module turns a public marketing folder into a private or semi-private entry point. If the linked `loyalty.card` or `folder.access.code` is expired or deactivated, all folder-prefixed navigation becomes inaccessible unless the user provides a fresh valid code.
