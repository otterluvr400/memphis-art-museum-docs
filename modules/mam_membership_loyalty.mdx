## Business Logic

<Steps>
  <Step title="Configure a subscription plan with a benefits pricelist">
    A user opens `sale.subscription.plan` and selects a `product.pricelist` in the `Benefits Pricelist` field on the form. The view is `sale_subscription_plan_form_inherit_benefit` (`views/sale_subscription_plan_views.xml`).
  </Step>
  <Step title="Create or change a subscription sale order">
    A `sale.order` with `is_subscription = True` and a `plan_id` that has a `benefit_pricelist_id` moves into or out of an active state (`3_progress`, `4_paused`, or `5_renewed`).
  </Step>
  <Step title="Sync the partner's pricelist">
    The overridden `sale.order._compute_subscription_state()` and `sale.order.write()` detect the state change and call `partner._sync_benefit_pricelist()` for the affected partners.
  </Step>
  <Step title="Grant or revoke the benefits pricelist">
    `_sync_benefit_pricelist()` searches for the newest active subscription (`order="id desc", limit=1`) for each partner. If found, it sets `partner.specific_property_product_pricelist` to the plan's `benefit_pricelist_id`. If no active subscription exists and the current pricelist is a benefit pricelist, it clears the field.
  </Step>
  <Step title="Daily background reconciliation">
    The `ir.cron` record `ir_cron_sync_benefit_pricelists` runs `_cron_sync_benefit_pricelists()` once per day. It searches for partners who either (a) currently hold a benefit pricelist, or (b) have any `sale.order` with `is_subscription = True`, and re-synchronizes them.
  </Step>
</Steps>

<Info>
  The active-state whitelist is defined as `BENEFIT_ACTIVE_STATES = ("3_progress", "4_paused", "5_renewed")` in `models/res_partner.py`. Only these states grant a pricelist; any other state (for example `2_renewal_draft`, `6_closed`, or `1_draft`) causes the pricelist to be removed if it is a benefit pricelist.
</Info>

<Warning>
  Confidence: **medium** — the `id desc` ordering means the newest sale order record wins, not necessarily the most recently updated subscription. If multiple active subscriptions with different plans exist, the newest one by database id determines the pricelist.
</Warning>

## Troubleshooting

- **Pricelist not applied when a subscription becomes active:** Confirm that the subscription plan has a non-empty `benefit_pricelist_id` and that the `sale.order` `subscription_state` is in `3_progress`, `4_paused`, or `5_renewed`. The `write()` override only triggers sync when `subscription_state` is explicitly in `vals`; the `_compute_subscription_state()` override triggers for any computed state change on an existing subscription.
- **Pricelist not removed after a subscription is closed:** The `write()` override captures `partner_id` before calling `super().write(vals)` when `subscription_state` is in `vals`, then re-synchronizes those partners. If state changes through a path that bypasses `write()` (for example direct SQL, or a computed field update not reflected in `vals`), the partner may not be re-synced until the next cron run.
- **Wrong pricelist when multiple active subscriptions exist:** The sync logic selects `order="id desc", limit=1`, so the newest `sale.order` by database id wins, not the highest-priority plan. If two plans have different benefit pricelists, ensure the desired subscription is the newest record or consider adding priority logic.
- **Cron not running:** The cron record `ir_cron_sync_benefit_pricelists` is created with `noupdate="1"`, so it will not be overwritten on upgrades after the first installation. If the cron was deleted or disabled, reinstalling or manually recreating the record is required.
- **Implied group not applied to existing users:** Adding `base.group_user` to the implied groups of `product.group_product_pricelist` affects users who are already members of the target group at the time the XML is loaded; new users inherit it automatically through the group hierarchy. If existing users appear to lack pricelist access after upgrade, verify whether the security record was applied by checking the group's "Inherited" tab.

## Native Odoo 19 Comparison

### `sale.order._compute_subscription_state()`

**Native Odoo 19:** The base `sale_subscription` module computes the `subscription_state` field from the order's subscription lifecycle fields. It does not trigger any partner-level pricelist synchronization when the state changes.

**This module:** The override captures the previous state for each record, calls `super()` to let the native computation run, then filters records whose `subscription_state` actually changed and calls `changed.mapped("partner_id")._sync_benefit_pricelist()`.

**Why it matters:** The subscription state machine is extended with a side effect that updates the partner's `specific_property_product_pricelist`. Developers should be aware that changing subscription state now performs a write on `res.partner`, which may trigger additional recomputations or audit entries.

### `sale.order.write()`

**Native Odoo 19:** The base `sale.order` `write()` method updates the order fields and recomputes dependent fields. It does not have a subscription-state side effect.

**This module:** If `subscription_state` is present in `vals`, the override collects the partner ids before the write, executes the base write, and then calls `_sync_benefit_pricelist()` on those partners. This covers state changes that arrive directly through `write()` rather than through the compute method.

**Why it matters:** This is a defensive second hook. It ensures that even when a state is written directly (for example by a wizard, import, or cron), the partner pricelist is updated. Developers adding new subscription state transitions should verify that `subscription_state` is in the written values, or explicitly call `_sync_benefit_pricelist()` on the partners.

### `res.partner.specific_property_product_pricelist`

**Native Odoo 19:** `res.partner` uses a property field `property_product_pricelist` to store the per-company pricelist, and `specific_property_product_pricelist` is the field that resolves the effective company-specific pricelist. It is normally set manually by users in the partner form or by automated pricelist assignment logic (for example website/eCommerce rules).

**This module:** The module writes `specific_property_product_pricelist` directly to grant or revoke a pricelist based on subscription state. It only modifies the field when the target is a benefits pricelist (a pricelist linked to any `sale.subscription.plan` via `benefit_pricelist_id`), and only clears it when the current value is a benefits pricelist.

**Why it matters:** The module is intentionally conservative: it will not overwrite a manually assigned non-benefit pricelist, and it will not clear a non-benefit pricelist even if no active subscription exists. However, it will overwrite any manually selected benefit pricelist if a subscription state change occurs, so partner-level pricelist management and the automated benefit system should not be used simultaneously for the same pricelist records.

### `sale.subscription.plan.benefit_pricelist_id`

**Native Odoo 19:** `sale.subscription.plan` stores pricing, billing, and self-service configuration for subscription plans. It does not have a native field linking a pricelist to membership benefits.

**This module:** The module adds `benefit_pricelist_id` to the plan model and exposes it on the plan form under a `Membership Benefits` group. Any active subscriber of that plan receives the selected pricelist.

**Why it matters:** This creates a new coupling between subscription plans and sales pricelists. A plan that is intended only for normal subscription pricing should leave `benefit_pricelist_id` empty; otherwise, every active subscriber will receive the benefit pricelist automatically.
