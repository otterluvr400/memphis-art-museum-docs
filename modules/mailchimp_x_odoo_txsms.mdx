# Business Logic

<Steps>
  <Step title="Configuration">
    `SmsApiMandrill._mandrill_config()` reads `ir.config_parameter` for `mandrill.api_key` and `mandrill.from_number`. Both must be set via Settings → Technical → System Parameters (or shell). The API key (`md-...` prefix) and from number (E.164 format, e.g. `+19018786017`) are never committed to the repository.
  </Step>
  <Step title="Number normalization">
    `SmsApiMandrill._to_e164()` strips non-digits, prefixes bare 10-digit US numbers with `+1`, and passes through existing `+` prefixes. Returns `False` for unparseable input.
  </Step>
  <Step title="SMS transport">
    `SmsApiMandrill._mandrill_send_one()` builds a JSON payload for the Mandrill `messages/send-sms` endpoint (`https://mandrillapp.com/api/1.1/messages/send-sms`). It uses a `requests.Session` with a 10-second timeout. Responses are parsed for per-recipient status (`sent`, `queued`, `invalid`, `rejected`). Authentication and configuration errors are mapped to custom failure types (`mandrill_auth`, `mandrill_rejected`, `mandrill_unconfigured`).
  </Step>
  <Step title="Batch sending">
    `SmsApiMandrill._send_sms_batch()` iterates over `messages` (dicts with `content` and `numbers` lists), calls `_mandrill_send_one()` per number, and returns a list of result dicts (`uuid`, `state`, `failure_reason`). This matches the `SmsApiBase._send_sms_batch` contract.
  </Step>
  <Step title="Global routing">
    `res.company._get_sms_api_class()` returns `SmsApiMandrill` globally for all companies. `sms.sms._split_by_api()` yields `SmsApiMandrill` directly, bypassing the company-based API class resolution that the base `sms` module uses. This means even if another module (e.g. `sms_twilio`) is installed, Mandrill will still take precedence unless `mailchimp_x_odoo_txsms` is uninstalled or its overrides are patched.
  </Step>
</Steps>

# Troubleshooting

- **SMS not sending** — Verify `mandrill.api_key` and `mandrill.from_number` are set in `ir.config_parameter`. The API key should start with `md-`.
- **"Mandrill is not configured" error** — One or both config parameters is missing. Check Settings → Technical → System Parameters.
- **"Mandrill authentication failed" error** — The API key is invalid or expired. Verify the key in the Mailchimp Transactional dashboard.
- **Number format rejected** — Ensure phone numbers are valid US numbers (10 digits) or E.164 (`+1...`). The `_to_e164()` normalizer handles most common formats but may fail on international numbers without a `+` prefix.
- **Mandrill unreachable** — Check network connectivity to `https://mandrillapp.com/api/1.1/messages/send-sms`. The timeout is 10 seconds.
- **Other SMS modules not working** — `sms.sms._split_by_api()` bypasses `res.company._get_sms_api_class()`, so installing `sms_twilio` or another provider module will not override Mandrill while `mailchimp_x_odoo_txsms` is installed.

# Native Odoo 19 Comparison

### `res.company._get_sms_api_class`

**Native Odoo 19:** Returns `SmsApi` (IAP-based SMS gateway) by default. Other provider modules (e.g. `sms_twilio`) can override this to return their own API class based on a company setting.

**This module:** Returns `SmsApiMandrill` unconditionally for all companies.

**Why it matters:** All SMS traffic is routed through Mandrill regardless of company configuration or other installed provider modules.

### `sms.sms._split_by_api`

**Native Odoo 19:** Yields the API class returned by `res.company._get_sms_api_class()`.

**This module:** Yields `SmsApiMandrill` directly, bypassing company-based resolution.

**Why it matters:** Even if another module overrides `_get_sms_api_class()`, the `_split_by_api()` override here ensures Mandrill is always used. This is a deliberate global-scope choice.
