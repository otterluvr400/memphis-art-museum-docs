## Business Logic

### SimpleTix event import flow

<Steps>
  <Step title="Start import">
    `action_start_import` resets counters, clears prior failures, and activates `ir_cron_simpletix_import` with `nextcall` set to now.
  </Step>
  <Step title="Cron batch">
    `_cron_import_batch` finds a running source and calls `_process_batch`.
  </Step>
  <Step title="List page">
    `_list_events_page` POSTs to `/manager/EventService/GetAllEvent` with `rows=10` and the current page number.
  </Step>
  <Step title="Import one event">
    `_import_one` fetches event details and tickets, creates or updates `event.event`, then attaches `event.event.ticket` records to the event product variant.
  </Step>
  <Step title="Failure handling">
    Each event gets two attempts with a 10-second pause; failures are written to `mam.simpletix.import.failure`.
  </Step>
  <Step title="Finish">
    When all pages are processed, `import_state` becomes `done` and the cron job is deactivated.
  </Step>
</Steps>

### Square catalog import flow

<Steps>
  <Step title="Start import">
    `action_start_import` initializes the phase machine (`fetch_categories`), deletes old failures, and triggers `ir_cron_square_import` immediately.
  </Step>
  <Step title="Fetch categories">
    `_phase_fetch_categories` paginates `/v2/catalog/list?types=CATEGORY`, syncs them to `product.category`, and stores a `cat_map` in `import_context`.
  </Step>
  <Step title="Fetch items">
    `_phase_fetch_items` paginates `/v2/catalog/list?types=ITEM` into `import_context`, using `import_cursor` for resume.
  </Step>
  <Step title="Fetch inventory">
    `_phase_fetch_inventory` POSTs `/v2/inventory/batch-retrieve-counts` for `SQUARE_STORE_LOCATION` and stores counts keyed by variation ID.
  </Step>
  <Step title="Process items">
    `_phase_process_items` processes 20 items per tick, creating/updating `product.template`, variants, prices, images, and `stock.quant` records.
  </Step>
  <Step title="Reschedule">
    `_schedule_next_tick` re-triggers the cron while `import_state == 'running'`.
  </Step>
</Steps>

### DeepSeek event categorization flow

`action_start_categorize` queues all `event.event` records with `sub_category == False`, activates `ir_cron_deepseek_categorize`, and starts a budgeted batch loop. `_process_batch` runs for up to 50 seconds per cron tick, calling DeepSeek for each event and writing the matching `product.category` child record into `event.sub_category`. Categorization is gated by `event.primary`; only subcategories under the primary category are considered.

<Warning>
  `event.primary` and `event.sub_category` are referenced in `deepseek_categorizer.py`
  but are not defined in this module. Confidence on their model/type is **low**.
</Warning>

## Troubleshooting

- **Import stalls:** Square import uses `self.env.cr.commit()` inside phase methods; a crash in mid-phase can leave `import_context` in a half-written state. Inspect `import_context` JSON before restarting.
- **Duplicate cron jobs:** `mam.square.source._get_runner_cron` creates a new cron if the XML reference is missing. Upgrades may leave duplicate runners if the XML ID lookup fails.
- **Empty Supabase import:** `import_customers` is a stub returning `[]`. Expect no data movement until implemented.
- **Missing product variant on event create:** SimpleTix import expects `event.product_id.product_variant_id` to exist immediately after `event.event` create. This relies on the `header_replacer` dependency; if that module is absent or changed, ticket creation fails.
- **Hard-coded Square location:** `SQUARE_STORE_LOCATION = "L8SBQM6SAFQFF"` is hard-coded in `square_object_source.py`. Inventory will not update correctly if the Square store location changes.
- **Generic `name` references:** Several models have a `name` field inherited from the mixin. When debugging, verify which source model is in scope.

## Native Odoo 19 Comparison

### `mam.square.source.import_objects`

**Native Odoo 19:** Scheduled jobs run once per interval as a single transaction; long-running imports typically rely on queue jobs (`queue_job`) or base import wizards.

**This module:** Implements a custom phase machine inside a one-minute cron. Each phase calls `env.cr.commit()` to persist intermediate state, and `_schedule_next_tick` re-triggers the same cron immediately until done.

**Why it matters:** A phase can survive a worker timeout or restart, but it breaks Odoo's normal transaction rollback semantics and can leave partial imports if a phase fails.

### `product.template` / `product.product` Square IDs

**Native Odoo 19:** Products are matched by internal database IDs or barcode/reference fields such as `default_code`.

**This module:** Adds `x_square_item_id` on `product.template`, `x_square_variation_id` on `product.product`, and `x_square_id` on `product.category` to upsert Square catalog objects.

**Why it matters:** Matching depends entirely on these custom fields; deleting or renaming them breaks incremental Square sync.

### `event.event.simpletix_event_identifier`

**Native Odoo 19:** Events track external identifiers through their own reference fields or integrations like `event_sale`.

**This module:** Adds `simpletix_event_identifier` directly to `event.event` and uses it as the upsert key for SimpleTix imports.

**Why it matters:** Imported events are linked to SimpleTix by this single custom field; duplicate protection relies on it being indexed and copy-protected.

### DeepSeek categorizer

**Native Odoo 19:** No LLM categorization is built in.

**This module:** Calls an external DeepSeek chat-completion endpoint with a hard-coded system prompt and writes the chosen category to `event.sub_category`.

**Why it matters:** Results depend on the model's adherence to the allowed category list and on the presence of `event.primary`/`event.sub_category` fields defined elsewhere.
